## 🗄️ IndexedDB (JavaScript Deep Dive)

This is a **🔴 Advanced + Practical Topic** — interviewers expect understanding of **why it exists, async behavior, transactions, and when to use it over localStorage/sessionStorage**.

---

# 🔹 Definition

👉 **IndexedDB** is a **low-level, browser-based NoSQL database** used to store large amounts of structured data on the client.

- Stores data as **objects (not just strings)**
- Works **asynchronously**
- Supports **indexes and transactions**

💡 Simple interview line:

> “IndexedDB is a client-side NoSQL database that allows storing large, structured data asynchronously in the browser.”

---

# 🔹 Core Explanation

---

## 🧠 1. Why IndexedDB Exists

👉 Problem with localStorage/sessionStorage:

- Only strings ❌
- Small size (~5MB) ❌
- Synchronous (blocking) ❌

---

👉 IndexedDB solves:

- Large storage ✅
- Structured data ✅
- Non-blocking (async) ✅

---

---

## 🧩 2. Key Concepts

---

### 🗂️ Database

- Top-level container

---

### 📦 Object Store

- Like a table (stores data)

---

### 🔑 Key

- Unique identifier

---

### 📊 Index

- Used for searching/filtering

---

### 🔄 Transaction

- Ensures safe operations

---

💡 Analogy:

> Database = Folder, Object Store = File, Index = Search

---

## ⚙️ 3. How It Works (Flow)

---

### Step 1: Open DB

```js id="idb1"
const request = indexedDB.open("MyDB", 1);
```

---

### Step 2: Create Schema (on upgrade)

```js id="idb2"
request.onupgradeneeded = (event) => {
  const db = event.target.result;
  db.createObjectStore("users", { keyPath: "id" });
};
```

---

### Step 3: Add Data

```js id="idb3"
const db = request.result;
const tx = db.transaction("users", "readwrite");
const store = tx.objectStore("users");

store.add({ id: 1, name: "Dilip" });
```

---

### Step 4: Read Data

```js id="idb4"
const getRequest = store.get(1);

getRequest.onsuccess = () => {
  console.log(getRequest.result);
};
```

---

## 🧠 WHY async?

- Avoid blocking main thread
- Handle large data efficiently

---

---

# 🔹 Tricky Behavior (Interview Focus)

---

## ⚠️ 1. Everything is Asynchronous

👉 Unlike localStorage:

```js id="idb5"
const data = store.get(1);
console.log(data); // ❌ not actual data
```

---

💡 Must use:

- callbacks
- promises (wrapped)

---

---

## ⚠️ 2. Versioning Required

```js id="idb6"
indexedDB.open("MyDB", 2);
```

---

👉 WHY:

- Schema updates require version change

---

---

## ⚠️ 3. Transactions Auto-Close

👉 If you don’t use transaction properly → it closes

---

💡 Must perform operations within transaction lifecycle

---

---

## ⚠️ 4. Complex API

👉 Native API is verbose and hard to use

---

💡 Solution:

- Use wrappers like `idb`, Dexie.js

---

# 🔹 Example (Simplified with Promise Wrapper)

---

```js id="idb7"
function openDB() {
  return new Promise((resolve, reject) => {
    const req = indexedDB.open("MyDB", 1);

    req.onsuccess = () => resolve(req.result);
    req.onerror = () => reject(req.error);
  });
}
```

# 🔹 When to Use / NOT Use

---

### ✅ Use IndexedDB when:

- Large data storage
- Offline-first apps
- Complex querying needed

---

### ❌ Avoid when:

- Simple key-value storage
  👉 Use localStorage instead

---

# 🔹 Common Mistakes / Traps

---

## ❌ Treating it like localStorage

👉 It’s async and complex

---

## ❌ Ignoring transactions

👉 Leads to data inconsistency

---

## ❌ Not handling versioning

👉 Causes schema issues

---

## ❌ Using raw API directly

👉 Leads to messy code

---

# 🔹 Advantages & Pitfalls

---

## ✅ Advantages

- Large storage capacity
- Supports structured data
- Async (non-blocking)
- Index-based queries

---

## ⚠️ Pitfalls

- Complex API
- Hard to debug
- Requires boilerplate
- Browser differences

---

# 🔹 Best Practices

✔ Use wrapper libraries (Dexie, idb)
✔ Design schema properly
✔ Use indexes for querying
✔ Handle version upgrades carefully
✔ Avoid unnecessary transactions
