# 🧠 Custom Errors in JavaScript

---

## 🔹 Definition

👉 **Simple Definition (2–3 lines):**
Custom errors are user-defined error types created to represent specific failure scenarios in your application.
They extend the built-in `Error` class.

👉 **Deeper Explanation (2–3 lines):**
Instead of throwing generic errors, custom errors allow you to provide **meaningful context, type, and structure**.
They improve debugging, error handling, and maintainability.

---

# 🔹 Deep Explanation (Core Section)

---

## 1️⃣ Why Custom Errors?

- Built-in errors (`TypeError`, `ReferenceError`) are too generic
- Custom errors help describe **business/domain-specific problems**

💡 Example:

- `ValidationError`, `AuthError`, `ApiError`

💡 Why important:

- Enables **fine-grained error handling**

---

## 2️⃣ Creating Custom Error (Extending `Error`)

```js
class MyError extends Error {}
```

- Inherits properties:
  - `message`
  - `stack`
  - `name`

💡 Internals:

- JS creates prototype chain:

```js
MyError.prototype.__proto__ === Error.prototype;
```

⚠️ Important:

- Must call `super(message)`

---

## 3️⃣ Adding Custom Properties

```js
class ValidationError extends Error {
  constructor(message, field) {
    super(message);
    this.field = field;
  }
}
```

- You can attach extra data

💡 Why:

- Helps in UI or logging

---

## 4️⃣ Setting `name` Property

```js
this.name = "ValidationError";
```

- Default name is `"Error"`

💡 Why:

- Helps identify error type

⚠️ Edge Case:

- Without setting name → confusing logs

---

## 5️⃣ Throwing Custom Errors

```js
throw new ValidationError("Invalid email", "email");
```

- Works same as built-in errors

💡 Internals:

- Creates error object → stops execution

---

## 6️⃣ Catching Specific Errors

```js
try {
} catch (e) {
  if (e instanceof ValidationError) {
  }
}
```

💡 Why:

- Allows different handling logic

⚠️ Edge Case:

- `instanceof` fails across iframes

---

## 7️⃣ Custom Errors in Async Code

```js
async function test() {
  throw new CustomError("Fail");
}
```

- Converted into rejected promise

💡 Must handle via:

- `try-catch` with `await`
- `.catch()`

---

## 8️⃣ Error Wrapping (Advanced)

```js
try {
  risky();
} catch (e) {
  throw new AppError("Wrapped", e);
}
```

- Wrap lower-level errors

💡 Why:

- Preserve original context

# 🔹 Example(s) with Code

---

## ✅ Example 1: Basic Custom Error

```js
class ValidationError extends Error {
  constructor(message) {
    super(message);
    this.name = "ValidationError";
  }
}

try {
  throw new ValidationError("Invalid input");
} catch (e) {
  console.log(e.name, e.message);
}
```

### 🔍 Execution:

1. Custom error created
2. Thrown inside try
3. Caught in catch

💡 Output:

```js
ValidationError Invalid input
```

💡 WHY:

- Custom name + message used

---

## ⚡ Example 2: Custom Properties

```js
class ApiError extends Error {
  constructor(message, status) {
    super(message);
    this.status = status;
  }
}

try {
  throw new ApiError("Not Found", 404);
} catch (e) {
  console.log(e.status);
}
```

### 🔍 Execution:

- Error carries extra info

💡 Output:

```js
404;
```

💡 WHY:

- Custom property attached

---

## ⚡ Example 3: Tricky `instanceof`

```js
class MyError extends Error {}

const err = new MyError("Oops");

console.log(err instanceof Error);
console.log(err instanceof MyError);
```

### 🔍 Execution:

- Prototype chain checked

💡 Output:

```js
true;
true;
```

💡 WHY:

- Inheritance maintained

# 🔹 Common Mistakes / Traps

---

### ❌ Mistake 1: Not calling super()

- ❌ Works fine
- ✅ Breaks error properties
- 💡 message/stack not set

---

### ❌ Mistake 2: Not setting name

- ❌ Default is fine
- ✅ Hard to debug
- 💡 Always set name

---

### ❌ Mistake 3: Throwing plain objects

```js
throw { msg: "error" };
```

- ❌ Same as Error
- ✅ Loses stack trace
- 💡 Use Error class

---

### ❌ Mistake 4: Ignoring instanceof

- ❌ Catch all errors same
- ✅ Handle specifically
- 💡 Better control
