## 🧠 Custom Errors (JavaScript)

---

## 🔹 Definition

Custom errors are **user-defined error types** that extend the built-in `Error` object to represent **specific business or application-level failures**.

👉 In simple terms:

> “Instead of throwing generic errors → create meaningful, domain-specific errors”

💡 Example:

- ❌ `Error: Something went wrong`
- ✅ `ValidationError: Email is invalid`

---

## 🔹 Core Explanation

---

### ⚙️ Why Custom Errors?

- Built-in errors (`TypeError`, `ReferenceError`) are too generic
- Real apps need **meaningful error classification**
- Helps in:
  - Better debugging
  - Specific error handling
  - Clean architecture

👉 Think like:

> “Different problems → different error types”

---

### 🧩 How Custom Errors Work

- Extend the `Error` class
- Add custom properties (name, status, code, etc.)
- Throw using `throw new CustomError()`

```js id="d92zv5"
class CustomError extends Error {
  constructor(message) {
    super(message);
    this.name = "CustomError";
  }
}
```

---

### 🔁 Error Properties (Important)

Every error object has:

```js id="4xqj6y"
error.name; // Error type
error.message; // Description
error.stack; // Stack trace
```

👉 Custom errors can extend this with:

- `statusCode`
- `errorCode`
- `metadata`

---

## 🔹 Example(s) with Code

---

### ✅ 1. Basic Custom Error

```js id="5l0t34"
class ValidationError extends Error {
  constructor(message) {
    super(message);
    this.name = "ValidationError";
  }
}

try {
  throw new ValidationError("Invalid input");
} catch (err) {
  console.log(err.name); // ValidationError
  console.log(err.message); // Invalid input
}
```

---

### ✅ 2. Adding Custom Properties (Important 🔥)

```js id="hcr81j"
class ApiError extends Error {
  constructor(message, statusCode) {
    super(message);
    this.name = "ApiError";
    this.statusCode = statusCode;
  }
}

throw new ApiError("Not Found", 404);
```

👉 Helps in:

- HTTP handling
- Backend/frontend communication

---

### ✅ 3. Conditional Error Handling

```js id="7r4o4p"
try {
  throw new ValidationError("Invalid email");
} catch (err) {
  if (err instanceof ValidationError) {
    console.log("Handle validation error");
  } else {
    console.log("Generic error");
  }
}
```

🧠 WHY:

- `instanceof` helps differentiate error types

---

### ✅ 4. Real-world Pattern (Advanced ⭐)

```js id="w06k4z"
class AppError extends Error {
  constructor(message, code) {
    super(message);
    this.name = this.constructor.name;
    this.code = code;
  }
}

class AuthError extends AppError {}
class PaymentError extends AppError {}
```

👉 Enables:

- Structured error hierarchy
- Clean scalable architecture

## 🔹 Real-world Use Cases

---

```js id="n0y68n"

  throw new ValidationError("Email required");
```

---

### 📡 2. API Error Handling

```js id="6c1rzi"
if (response.status !== 200) {
  throw new ApiError("API failed", response.status);
```

### 🔐 3. Authentication Errors

```js id="p31zqj"
throw new AuthError("Token expired");
```

---

### 🧱 4. Clean Architecture

- Separate error types:
  - Validation
  - Network
  - Business logic

## 🔹 When to Use / When NOT to Use

---

### ✅ Use

- When you need **specific error handling**
- Large applications with multiple modules
- APIs and validation logic

---

### ❌ Avoid

- For very small scripts (overkill)
- When generic error is sufficient

---

## 🔹 Common Mistakes / Traps

---

### ❌ Mistake 1: Not extending Error properly

```js id="9u7fym"
class MyError {} ❌
```

👉 Must extend:

```js id="lht6zr"
class MyError extends Error {}
```

---

### ❌ Mistake 2: Forgetting `super(message)`

👉 Without this:

- `message` won’t be set properly

---

### ❌ Mistake 3: Not setting `name`

👉 Leads to confusing logs:

```js id="s7d9jx"
Error: message ❌
```

---

### ❌ Mistake 4: Not using `instanceof`

👉 Can’t differentiate error types properly

## 🔹 Interview Q&A

---

### ❓1. What are custom errors?

User-defined error classes used to represent specific application errors.

---

### ❓2. Why extend `Error` class?

To inherit standard error behavior like stack trace and message.

---

### ❓3. What is `instanceof` used for?

To check error type and handle it accordingly.

---

### ❓4. Can we add custom properties?

✅ Yes, like `statusCode`, `errorCode`.

---

### ❓5. Difference between `throw new Error` vs custom error?

- Generic vs domain-specific error
- Custom errors provide better control

---

### ❓6. Are custom errors useful in frontend?

✅ Yes, especially for API, validation, and UI handling.

---

### ❓7. Can custom errors be used with async?

✅ Yes, with `try-catch` + `await`.

---

### ❓8. What is error hierarchy?

Creating parent-child error classes for structured handling.
