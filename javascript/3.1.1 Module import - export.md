## 📦 Module: `import` – `export` (ES Modules)

---

## 🔹 Definition

**`import` and `export`** are ES6 features that allow you to **split code into reusable modules** and share functionality between files.

👉 In simple terms:

- `export` → expose variables/functions/classes from a file
- `import` → use them in another file

💡 This helps in writing **clean, maintainable, and scalable code** instead of putting everything in one file.

---

## 🔹 Core Explanation

### 📤 1. `export` (Making things available)

- `export` is used to expose variables, functions, or classes from a module so other files can use them.
- A file becomes a **module automatically** when it uses `export` or `import`.
- You can have **multiple named exports** or **one default export** per file.

---

### 📥 2. `import` (Using exported things)

- `import` allows you to bring exported members from another file.
- It works **statically (at compile time)**, meaning imports are resolved before execution.
- This enables optimizations like **tree-shaking (removing unused code)**.

---

### 🔄 3. Types of Exports

#### ✅ Named Export

- Multiple exports per file
- Must import using **exact same name**

```js
// math.js
export const add = (a, b) => a + b;
export const sub = (a, b) => a - b;
```

```js
// app.js
import { add, sub } from "./math.js";
```

---

#### ✅ Default Export

- Only **one default export per file**
- Import name can be anything

```js
// user.js
export default function getUser() {
  return "Dilip";
}
```

```js
// app.js
import getUser from "./user.js";
```

---

### 🔀 4. Mixing Default + Named

```js
// utils.js
export const PI = 3.14;
export default function greet() {
  return "Hello";
}
```

```js
import greet, { PI } from "./utils.js";
```

---

### 🔁 5. Renaming Imports/Exports

```js
// export
export { add as sum };

// import
import { sum } from "./math.js";
```

👉 Useful when names clash or for readability.

---

### 📦 6. Import All (`* as`)

```js
import * as math from "./math.js";

math.add(2, 3);
```

👉 Groups all exports into a single object.

---

### ⚙️ How It Works Internally (Important 🔥)

- ES Modules use **static analysis** → imports are resolved before code runs
- Unlike CommonJS (`require`), ES Modules are:
  - **Hoisted**
  - **Read-only bindings** (you cannot reassign imported variables)

```js
import { count } from './counter.js';
count = 10; ❌ // Error (read-only)
```

💡 But if object is imported:

```js
import { obj } from './file.js';
obj.value = 10; ✅ // allowed (mutation, not reassignment)
```

---

## 🔹 Example (Execution Understanding)

```js
// counter.js
export let count = 0;
export function increment() {
  count++;
}
```

```js
// app.js
import { count, increment } from "./counter.js";

console.log(count); // 0
increment();
console.log(count); // 1 ✅
```

### 🔍 Why it works?

- ES Modules use **live bindings**
- Imported values are **not copied**, they are **linked references**

👉 So when `count` changes in `counter.js`, it reflects everywhere.

## 🔹 Real-world Use Cases

### 🧩 1. Component-based architecture (React)

- Each component in a separate file
- Export component → Import wherever needed

```js
export default Button;
```

---

### 📦 2. Utility functions

- Create a `utils.js` file
- Export reusable functions like formatting, validation

---

### 🧱 3. API layer separation

- Keep API calls in one file
- Import into components/services

---

## 🔹 When to Use / When NOT

### ✅ Use when:

- Project is modular (React, Angular, etc.)
- Code needs reusability and separation of concerns
- Working with modern bundlers (Vite, Webpack)

### ❌ Avoid when:

- Very small scripts (overkill)
- Legacy environments without module support (unless transpiled)

## 🔹 Common Mistakes / Traps

### ❌ Mistake 1: Confusing default vs named

```js
import { myFunc } from './file.js'; ❌ (if default export)
```

```js
import myFunc from './file.js'; ✅
```

---

### ❌ Mistake 2: Forgetting file extension (in browser)

```js
import x from './file'; ❌
import x from './file.js'; ✅
```

---

### ❌ Mistake 3: Assuming copy instead of reference

```js
import { count } from "./file.js";
```

👉 Developers think it's a copy
👉 Actually it's a **live binding**

---

### ❌ Mistake 4: Dynamic import confusion

```js
import("./module.js"); // async
```

👉 Returns a **Promise**, not immediate value

## 🔹 Interview Q&A

### ❓ 1. Difference between default and named export?

- Named exports allow multiple exports per file and require exact names.
- Default export allows only one and can be imported with any name.

---

### ❓ 2. Are imports hoisted?

- Yes, ES module imports are **hoisted** and resolved before execution.
- You can technically use imported variables before their declaration in code.

---

### ❓ 3. What are live bindings?

- Imported variables are **references, not copies**.
- Changes in the original module reflect in all importers.

---

### ❓ 4. Can you conditionally import modules?

- Static imports ❌ cannot be conditional
- Use `import()` (dynamic import) ✅

---

### ❓ 5. Difference between ES Modules and CommonJS?

- ES Modules → static, support tree-shaking
- CommonJS (`require`) → dynamic, runtime loading

---

### ❓ 6. Can we have multiple default exports?

- ❌ No, only one default export per file

---

### ❓ 7. What is tree-shaking?

- Removing unused exports during bundling
- Possible because ES Modules are statically analyzable

---

### ❓ 8. Why imports are read-only?

- To maintain **predictability and consistency** across modules
- Prevent accidental mutation of shared state

## 🔹 Advantages

✅ Better code organization
✅ Reusability
✅ Supports tree-shaking (smaller bundle size)
✅ Clear dependency management

---

## 🔹 Pitfalls

⚠️ Circular dependencies can cause unexpected behavior
⚠️ Must understand default vs named exports clearly
⚠️ Browser requires proper file paths/extensions

---

## 🔹 Best Practices

✔ Prefer **named exports** for utilities (better clarity)
✔ Use **default export for main entity** (like component/class)
✔ Keep modules **small and focused**
✔ Avoid circular dependencies
✔ Use consistent naming conventions

---

## 🔹 Senior-Level Insights 💡

### ⚡ 1. Tree-Shaking & Performance

- ES Modules enable bundlers (like Vite/Webpack) to remove unused code
- Helps reduce bundle size → faster load time

---

### ⚡ 2. Static vs Dynamic Import Trade-off

- Static import → faster, optimized
- Dynamic import → useful for **lazy loading** (code splitting)

```js
const module = await import("./heavy.js");
```

👉 Used in React for lazy loading routes/components

---

### ⚡ 3. Circular Dependency Problem

```js
// A imports B, B imports A
```

- Can lead to **undefined values during initialization**
- Happens because modules are loaded **partially**
