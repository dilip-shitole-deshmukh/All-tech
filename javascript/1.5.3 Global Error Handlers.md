## 🧠 Global Error Handlers (JavaScript)

---

## 🔹 Definition

Global error handlers are mechanisms to **catch errors that are not handled locally (try-catch)** anywhere in your application.

👉 In simple terms:

> “If an error slips through your code → global handler catches it”

💡 They act as a **last safety net** for your app.

---

## 🔹 Core Explanation

---

### ⚙️ Why Global Error Handlers are Needed

- Not all errors are caught using `try-catch`
- Async errors (Promises, events) often escape local handling
- Without global handling → app crashes silently or logs unclear errors

👉 So we use global handlers to:

- Log errors centrally
- Show fallback UI
- Prevent bad user experience

---

### ✅ 1. `window.onerror` (Classic Global Handler)

```js id="buxd7x"
window.onerror = function (message, source, lineno, colno, error) {
  console.log("Global Error:", message);
};
```

🧠 How it works:

- Captures **uncaught synchronous errors**
- Provides details:
  - message
  - file (source)
  - line/column

💡 Works for errors not caught anywhere else

---

### ✅ 2. `window.addEventListener('error')`

```js id="2nhbdi"
window.addEventListener("error", (event) => {
  console.log("Error:", event.message);
});
```

🧠 Difference from `window.onerror`:

- More flexible (multiple listeners allowed)
- Better for modern apps

---

### ✅ 3. `unhandledrejection` (Very Important 🔥)

```js id="e48z5k"
window.addEventListener("unhandledrejection", (event) => {
  console.log("Unhandled Promise:", event.reason);
});
```

🧠 Why needed:

- `try-catch` does NOT catch async Promise errors without `await`
- This handles **unhandled Promise rejections**

👉 Example:

```js id="v3a4t9"
Promise.reject("Error occurred");
```

💡 Without `.catch()` → global handler catches it

---

### 🔁 Sync vs Async Error Handling

| Type  | Local Handling    | Global Handling    |
| ----- | ----------------- | ------------------ |
| Sync  | try-catch         | window.onerror     |
| Async | try-catch + await | unhandledrejection |

## 🔹 Example(s) with Code

---

### ✅ Example 1: Uncaught Error

```js id="e2rth9"
function test() {
  console.log(a); // ReferenceError
}

test();
```

👉 Output:

- Not caught locally
- Global handler (`window.onerror`) triggers

---

### ✅ Example 2: Unhandled Promise

```js id="x9y7h4"
Promise.reject("Something failed");
```

👉 Output:

- `unhandledrejection` event fires

---

### ✅ Example 3: Async Try-Catch Trap ⚠️

```js id="z4y7od"
try {
  setTimeout(() => {
    throw new Error("Async Error");
  }, 1000);
} catch (e) {
  console.log("Caught");
}
```

🧠 Output:

- ❌ Not caught by try-catch
- ✅ Caught by global handler

💡 WHY:

- `setTimeout` runs later → outside try block execution

## 🔹 Real-world Use Cases

---

### 🌐 1. Error Logging (Very Important)

- Send errors to monitoring tools:
  - Sentry
  - LogRocket

```js id="y0m7ci"
window.onerror = function (msg, url, line) {
  sendToServer({ msg, url, line });
};
```

---

### 📉 2. Crash Reporting

- Track production issues
- Helps debugging real user problems

---

### 🎯 3. Fallback UI

- Show error page or message instead of blank screen

---

## 🔹 When to Use / When NOT to Use

---

### ✅ Use

- As a **fallback mechanism**
- Logging & monitoring
- Catch unexpected errors

---

### ❌ Avoid

- Replacing `try-catch` with global handlers
- Ignoring errors after catching
- Over-relying on global handling

---

## 🔹 Common Mistakes / Traps

---

### ❌ Mistake 1: Thinking it catches all errors

👉 It **does NOT catch**:

- Errors inside `try-catch`
- Handled promise rejections

---

### ❌ Mistake 2: Ignoring async errors

👉 Need `unhandledrejection` for promises

---

### ❌ Mistake 3: Silent failure

```js id="9sbd2x"
window.onerror = () => {};
```

👉 This hides bugs completely ❌

---

### ❌ Mistake 4: Using only one handler

👉 Modern apps should use:

- `error` + `unhandledrejection`

## 🔹 Interview Q&A

---

### ❓1. What are global error handlers?

Mechanisms to catch uncaught errors at application level.

---

### ❓2. Difference between `onerror` and `unhandledrejection`?

- `onerror` → sync errors
- `unhandledrejection` → async Promise errors

---

### ❓3. Can try-catch replace global handlers?

❌ No, it only handles local synchronous code.

---

### ❓4. Why async errors are tricky?

Because they execute later, outside current execution context.

---

### ❓5. Can global handlers prevent crashes?

They help log and recover, but cannot fully prevent logical failures.

---

### ❓6. What data do we get in onerror?

Message, file, line number, column, error object.

---

### ❓7. Should we show errors to users?

❌ No raw errors → show friendly messages instead.

---

### ❓8. Can multiple handlers exist?

✅ Yes, with `addEventListener`

---

## 🔹 Advantages / Pitfalls

---

### ✅ Advantages

- Centralized error handling
- Better debugging
- Improved monitoring

---

### ❌ Pitfalls

- Can hide bugs if misused
- Not a replacement for proper error handling
- Limited control over recovery

---

## 🔹 Best Practices

---

✔ Always log errors (don’t ignore)
✔ Use both `error` and `unhandledrejection`
✔ Send logs to monitoring tools
✔ Show user-friendly fallback UI
✔ Keep local try-catch for critical logic

---

1. Local try-catch

### 🧠 React/Frontend Architecture

- Use **Error Boundaries** for UI errors

---

### 🔄 Error Flow in Real Apps

```text
User Action → API Call → Error →
try-catch? → yes → handle
no → global handler → log + fallback
```

---

### ⚖️ Trade-offs

| Approach       | Pros             | Cons          |
| -------------- | ---------------- | ------------- |
| try-catch      | Precise control  | Limited scope |
| Global handler | Catch-all safety | Less control  |
