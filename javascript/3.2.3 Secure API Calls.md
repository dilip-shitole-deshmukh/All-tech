## 🔐 Secure API Calls (Deep Dive for Frontend Interviews)

This is a **🔴 Advanced + Real-world Topic**, because security involves **architecture, browser behavior, backend coordination, and attack prevention**.

---

# 🔹 Definition

👉 **Secure API Calls** mean making HTTP requests from frontend to backend in a way that **protects data, prevents unauthorized access, and avoids common attacks**.

- It involves **authentication, authorization, encryption, and safe data handling**
- Security is **NOT just backend — frontend plays a critical role**

💡 Simple interview line:

> “Secure API calls ensure that only authorized users can access APIs and that data is protected during transmission and usage.”

---

# 🔹 Core Concepts

---

## 🔑 1. HTTPS (Encryption Layer – MUST)

👉 Always use **HTTPS instead of HTTP**

- Encrypts data using TLS
- Prevents:
  - Man-in-the-middle attacks
  - Data interception

💡 Without HTTPS:

> Anyone on network can read your API data (tokens, passwords)

---

## 🔐 2. Authentication (Who are you?)

👉 Verifying user identity

### Common Methods:

### 🪪 a) JWT (JSON Web Token)

- Token issued after login
- Sent in headers:

```js id="jwt1"
fetch("/api/data", {
  headers: {
    Authorization: "Bearer <token>",
  },
});
```

---

### 🍪 b) Cookies (Session-based)

- Stored in browser
- Automatically sent with requests

💡 Secure cookie flags:

- `HttpOnly` → prevents JS access
- `Secure` → only over HTTPS

---

## 🛡️ 3. Authorization (What can you access?)

- After authentication, check permissions
- Example:
  - User → read data
  - Admin → delete data

💡 Done on backend, but frontend must:

- Hide restricted UI
- Avoid exposing sensitive actions

---

## ⚠️ 4. Common Security Threats

---

### 💥 a) XSS (Cross-Site Scripting)

👉 Attacker injects malicious JS

```html id="xss1"
<input value="<script>alert('hack')</script>" />
```

💡 Prevention:

- Escape user input
- Avoid `dangerouslySetInnerHTML` (React)

---

### 🔄 b) CSRF (Cross-Site Request Forgery)

👉 Unauthorized requests using user’s session

💡 Prevention:

- CSRF tokens
- SameSite cookies

---

### 🕵️ c) Token Leakage

👉 Storing tokens insecurely

❌ Bad:

```js id="bad1"
localStorage.setItem("token", token);
```

👉 Vulnerable to XSS

---

## 📦 5. Where to Store Tokens (Interview Favorite)

| Storage         | Secure? | Notes             |
| --------------- | ------- | ----------------- |
| localStorage    | ❌      | Vulnerable to XSS |
| sessionStorage  | ❌      | Same issue        |
| HttpOnly Cookie | ✅      | Safer             |

💡 Best practice:

> Use HttpOnly cookies for sensitive tokens

---

## 🔄 6. CORS (Cross-Origin Resource Sharing)

👉 Controls which domains can access your API

- Browser blocks unauthorized cross-origin requests
- Backend must allow trusted origins

Example:

```
Access-Control-Allow-Origin: https://myapp.com
```

---

## 🔒 7. API Rate Limiting

👉 Prevent abuse (DDOS, brute force)

- Limit number of requests per user/IP
- Protects backend

---

# 🔹 Example (Secure API Call)

```js id="secure1"
async function getProfile() {
  const res = await fetch("/api/profile", {
    method: "GET",
    credentials: "include", // for cookies
  });

  if (!res.ok) {
    throw new Error("Unauthorized");
  }

  return res.json();
}
```

---

## 🧠 Execution Notes

- `credentials: include` → sends cookies
- Backend validates session/token
- Response returned securely

# 🔹 Common Mistakes / Traps

## ❌ “Frontend security is not important”

👉 Wrong

- Frontend is entry point → many attacks happen here

---

## ❌ Storing JWT in localStorage

👉 Vulnerable to XSS

---

## ❌ Ignoring HTTPS in dev

👉 Leads to bad habits

---

## ❌ Exposing secrets in frontend

```js
const API_KEY = "123"; ❌
```

👉 Anyone can see this

---

# 🔹 Advantages & Pitfalls

## ✅ Advantages

- Protects user data
- Prevents unauthorized access
- Builds trust

---

## ⚠️ Pitfalls

- Adds complexity
- Requires backend coordination
- Misconfiguration leads to vulnerabilities

---

# 🔹 Best Practices

✔ Always use HTTPS
✔ Use HttpOnly + Secure cookies
✔ Implement proper authentication (JWT/OAuth)
✔ Validate input on frontend & backend
✔ Avoid exposing sensitive data
✔ Use environment variables
✔ Handle errors securely (don’t leak info)

# 🔹 Senior-Level Insights 🧠

---

## ⚡ 1. Token Strategy Trade-off

| Approach           | Pros   | Cons      |
| ------------------ | ------ | --------- |
| JWT (localStorage) | Easy   | XSS risk  |
| HttpOnly Cookie    | Secure | CSRF risk |

👉 Best approach:

- HttpOnly + CSRF protection

---

## 🔄 2. Refresh Token Flow

👉 Access token expires quickly
👉 Refresh token gets new one

💡 Improves:

- Security
- User experience

---

## 📊 3. Zero Trust Approach

- Never trust client
- Validate everything on backend

---

# 🔹 Interview Q&A 🎯

### 1. What is secure API call?

An API request made with proper authentication, encryption, and protection against attacks.

---

### 2. Why use HTTPS?

To encrypt data and prevent interception or man-in-the-middle attacks.

---

### 3. Where should JWT be stored?

Prefer HttpOnly cookies instead of localStorage for better security.

---

### 4. What is CORS?

A mechanism that controls cross-origin API access via browser security policies.

---

### 5. What is CSRF?

An attack where unauthorized requests are made using a user’s session.

---

### 6. How to prevent XSS?

Sanitize input, avoid unsafe DOM rendering, use frameworks safely.

---

### 7. What is authentication vs authorization?

Authentication verifies identity, authorization checks permissions.

---

### 8. What is refresh token?

A token used to get a new access token without re-login.

---

### 9. Why not store secrets in frontend?

Frontend code is visible to users → secrets can be exposed.

---

### 10. What is rate limiting?

Restricting number of API requests to prevent abuse.

---

# ✅ Final Summary (Interview Answer)

👉 “Secure API calls involve using HTTPS, proper authentication and authorization, and protecting against attacks like XSS and CSRF. Sensitive data should be handled carefully, typically using HttpOnly cookies and server-side validation. Security is a shared responsibility between frontend and backend.”
