## 👉 Functional Programming (FP)

---

## 🔹 Definition

👉 **Functional Programming** is a programming paradigm where:

- You build programs using **pure functions**
- Avoid **shared mutable state**
- Focus on **what to do**, not _how to do it_

📌 Simple:

> Write code using **functions + immutability + no side effects**

---

## 🔹 Core Explanation

### 🧠 1. Pure Functions (Foundation of FP)

- Functions should be **deterministic** (same input → same output).
- No side effects → no external dependency → easy to test and reason about.

💡 WHY it matters:

- Predictable behavior reduces bugs in large applications.

---

### 🔒 2. Immutability

- Instead of modifying existing data, you **create new data**.
- Prevents accidental state changes and improves debugging.

```js
// ❌ Mutation
user.name = "Dilip";

// ✅ Immutable
const updatedUser = { ...user, name: "Dilip" };
```

💡 WHY:

- Shared mutable state is one of the biggest sources of bugs.

---

### 🔁 3. First-Class & Higher-Order Functions

- Functions can be passed, returned, and stored.
- Enables powerful abstractions like `map`, `filter`, `reduce`.

```js
const nums = [1, 2, 3];
const result = nums.map((n) => n * 2);
```

💡 WHY:

- Helps write **declarative and reusable logic**

---

### 🔗 4. Function Composition

- Combining small functions to build complex logic.

```js
const add = (x) => x + 2;
const multiply = (x) => x * 3;

const compose = (f, g) => (x) => f(g(x));

const result = compose(multiply, add)(5); // (5+2)*3 = 21
```

💡 WHY:

- Encourages **small reusable functions instead of big complex ones**

---

### 🔄 5. Declarative vs Imperative

```js
// ❌ Imperative
let result = [];
for (let i = 0; i < arr.length; i++) {
  if (arr[i] > 2) result.push(arr[i] * 2);
}

// ✅ Declarative (FP style)
const result = arr.filter((x) => x > 2).map((x) => x * 2);
```

💡 WHY:

- Declarative code is **cleaner and easier to read**

---

### 🧩 6. Avoiding Side Effects

- FP tries to isolate side effects (API calls, DOM updates).
- Core logic remains pure.

💡 Pattern:

- **Pure core + Impure shell**

---

## 🔹 Example(s) with Code

### ✅ Example 1: Functional Approach

```js
const users = [
  { name: "A", age: 20 },
  { name: "B", age: 30 },
];

const getAdultNames = (users) =>
  users.filter((user) => user.age > 21).map((user) => user.name);

console.log(getAdultNames(users)); // ["B"]
```

🧩 **Why FP?**

- No mutation
- Uses HOFs (`filter`, `map`)
- Easy to read and test

---

### ⚠️ Example 2: Tricky Mutation Issue

```js
const arr = [1, 2, 3];

const double = (arr) => {
  arr.push(4);
  return arr.map((x) => x * 2);
};

console.log(double(arr)); // [2,4,6,8]
console.log(arr); // [1,2,3,4] ❗ mutated
```

👉 Problem:

- Function changes original array → not FP

## 🔹 Real-world Use Cases

### ⚛️ 1. React Development

- React encourages FP:
  - Components as functions
  - State immutability
  - Hooks rely on predictable behavior

---

### 🔄 2. Redux / State Management

- Reducers must be **pure functions**
- Enables debugging (time travel, undo/redo)

---

### 📊 3. Data Transformation

- APIs return raw data → FP transforms it cleanly
- Example: filtering, mapping, grouping

---

### ⚙️ 4. Utility Libraries

- Libraries like Lodash/Ramda follow FP principles
- Provide reusable functional helpers

---

## 🔹 When to Use / When NOT to Use

### ✅ Use FP When:

- Working with **state management**
- Data transformation (arrays, APIs)
- Building **predictable systems**

---

### ❌ Avoid Overusing FP When:

- Logic becomes too abstract (hard to read)
- Performance-critical code (excess object creation)
- Team is not comfortable with FP patterns

---

## 🔹 Common Mistakes / Traps

### ❌ Mistake 1: Thinking FP = only map/filter

👉 FP is more about **principles**, not just methods.

---

### ❌ Mistake 2: Mutating data unknowingly

```js
arr.sort(); // ❗ mutates original array
```

👉 Many built-in methods mutate → breaks FP

---

### ❌ Mistake 3: Over-composition

```js
compose(f1, f2, f3, f4, f5);
```

👉 Too many layers → hard to debug

---

### ❌ Mistake 4: Ignoring performance

- Creating new objects repeatedly can increase memory usage
- Not always ideal in tight loops

## 🔹 Interview Q&A

### ❓1. What is Functional Programming?

👉 A paradigm focused on pure functions, immutability, and avoiding side effects.

---

### ❓2. Difference between FP and OOP?

👉 FP focuses on functions and immutability, while OOP focuses on objects and state mutation.

---

### ❓3. Why is immutability important?

👉 Prevents unintended side effects and makes state predictable.

---

### ❓4. What is function composition?

👉 Combining multiple functions to build complex logic.

---

### ❓5. Are JavaScript methods like map/filter FP?

👉 Yes, they support FP because they use pure functions and avoid mutation.

---

### ❓6. Is FP always better?

👉 No. It improves predictability but may affect readability/performance if overused.

---

### ❓7. What is declarative programming?

👉 Describing _what to do_ instead of _how to do it_.

---

### ❓8. Why are reducers pure in Redux?

👉 To ensure predictable state transitions and enable debugging tools.

---

## 🔹 Advantages / Pitfalls

### ✅ Advantages

- Predictable and bug-resistant code
- Easier testing
- Better readability (declarative style)
- High reusability

---

### ⚠️ Pitfalls

- Learning curve for beginners
- Can become too abstract
- Memory overhead (due to immutability)

---

## 🔹 Best Practices

✔ Keep functions small and single-purpose
✔ Avoid mutation (`push`, `sort`, etc.)
✔ Use `map`, `filter`, `reduce` wisely
✔ Isolate side effects
✔ Prefer composition over nesting

---

## 🔹 Senior-Level Insights

### ⚡ 1. FP + React Performance

- Immutability enables:
  - Shallow comparison (`React.memo`)
  - Efficient re-rendering

💡 Without immutability → React can’t optimize properly

---

### ⚡ 2. Scalability

- FP scales well in large apps because:
  - Logic is isolated
  - No hidden dependencies

---

### ⚡ 3. Trade-offs

| Aspect         | FP Benefit             | Cost                     |
| -------------- | ---------------------- | ------------------------ |
| Predictability | High                   | More boilerplate         |
| Performance    | Good (optimized cases) | Extra memory allocations |
| Readability    | Clean (if used well)   | Can become abstract      |

---
