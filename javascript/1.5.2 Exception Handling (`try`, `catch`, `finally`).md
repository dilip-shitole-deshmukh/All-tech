# 🧠 Exception Handling in JavaScript

---

## 🔹 Definition

👉 **Simple Definition (2–3 lines):**
Exception handling is a mechanism to handle runtime errors gracefully without crashing the application.
It uses `try`, `catch`, and `finally` blocks to control error flow.

👉 **Deeper Explanation (2–3 lines):**
JavaScript executes risky code inside `try`, and if an error occurs, control jumps to `catch`.
`finally` runs regardless of success or failure, ensuring cleanup or final actions.

---

# 🔹 Deep Explanation (Core Section)

---

## 1️⃣ `try` Block (Execution Zone)

- Contains code that might throw an error
- If no error → executes normally
- If error occurs → execution stops immediately

💡 Internals:

- JS engine wraps this block in an internal error-handling context
- On exception → stack unwinding starts

⚠️ Edge Case:

- Syntax errors are NOT caught (they happen before execution)

---

## 2️⃣ `catch` Block (Error Handler)

```js
try {
} catch (err) {}
```

- Executes only if error occurs in `try`
- Receives error object

💡 Error Object contains:

- `name` → TypeError, ReferenceError
- `message` → error description
- `stack` → call stack

⚠️ Optional catch:

```js
catch { ... }
```

---

## 3️⃣ `finally` Block (Always Runs)

```js
finally { ... }
```

- Executes **always**, whether error occurs or not

💡 Use case:

- Cleanup operations (closing resources, loaders)

⚠️ Edge Case:

```js
finally {
  return "override";
}
```

- Overrides return from try/catch

---

## 4️⃣ Throwing Custom Errors

```js
throw new Error("Something went wrong");
```

- You can manually throw errors

💡 Why:

- Enforce validation rules
- Stop execution intentionally

⚠️ Edge Case:

- Throwing non-error values:

```js
throw "error"; // allowed but bad practice
```

---

## 5️⃣ Synchronous vs Asynchronous Errors

❗ VERY IMPORTANT INTERVIEW POINT

```js
try {
  setTimeout(() => {
    throw new Error("Error");
  }, 1000);
} catch (e) {
  console.log("Caught");
}
```

💡 Output:

- ❌ Not caught

💡 Why:

- `try-catch` works only for **synchronous code**
- Async errors handled via:
  - `.catch()` in promises
  - `try-catch` with `async/await`

---

## 6️⃣ `try-catch` with `async/await`

```js
try {
  await fetchData();
} catch (e) {}
```

- Works because `await` pauses execution

💡 Internals:

- Async function converts errors into rejected promises

---

## 7️⃣ Error Propagation (Bubble Up)

- If not handled → error propagates upward
- Eventually crashes program

💡 Call stack unwinding:

- Functions removed until handler found

---

## 8️⃣ Multiple `try-catch` Nesting

- Can nest try-catch blocks
- Inner catch handles local errors

⚠️ Overuse:

- Makes code messy

---

# 🔹 Example(s) with Code

---

## ✅ Example 1: Basic try-catch

```js
try {
  JSON.parse("invalid json");
} catch (e) {
  console.log("Error caught");
}
```

### 🔍 Execution:

1. `JSON.parse` throws error
2. Control jumps to catch
3. Logs message

💡 Output:

```js
Error caught
```

💡 WHY:

- Invalid JSON → runtime error

---

## ⚡ Example 2: finally override (Tricky)

```js
function test() {
  try {
    return "try";
  } catch {
    return "catch";
  } finally {
    return "finally";
  }
}

console.log(test());
```

### 🔍 Execution:

1. `try` returns "try"
2. `finally` executes after
3. Overrides return

💡 Output:

```js
finally
```

💡 WHY:

- `finally` has highest priority

---

## ⚡ Example 3: Async Error (Interview-Level)

```js
async function test() {
  try {
    throw new Error("Oops");
  } catch (e) {
    return "caught";
  }
}

test().then(console.log);
```

### 🔍 Execution:

1. Error thrown inside async
2. Converted to rejected promise
3. Catch handles it

💡 Output:

```js
caught;
```

💡 WHY:

- Async functions wrap errors

# 🔹 When to use? (Why, Where, How)

---

✔️ Use when:

- Code may fail at runtime
- API calls, parsing, external input

✔️ Use when:

- You want controlled failure

✔️ Use when:

- Using async/await

---

# 🔹 When NOT to use

---

❌ Avoid for:

- Normal control flow
- Replacing if-else

❌ Avoid:

- Catching errors and ignoring them

---

# 🔹 Common Mistakes / Traps

---

### ❌ Mistake 1: Expecting async catch

- ❌ try-catch catches setTimeout errors
- ✅ It doesn’t
- 💡 Async runs later

---

### ❌ Mistake 2: Ignoring error object

- ❌ Just log message
- ✅ Use error details
- 💡 Debugging harder

---

### ❌ Mistake 3: Overusing try-catch

- ❌ Wrap everything
- ✅ Use only risky code
- 💡 Performance + readability

---

### ❌ Mistake 4: Returning in finally

- ❌ Safe
- ✅ Overrides everything
- 💡 Dangerous bug

# 🔹 10+ Interview Q&A

---

### 1. What is try-catch?

Mechanism to handle runtime errors.

---

### 2. Does try-catch handle syntax errors?

No, syntax errors occur before execution.

---

### 3. What is finally?

Block that always executes after try/catch.

---

### 4. Can catch be omitted?

Yes, with only finally.

---

### 5. Can finally override return?

Yes, it overrides return values.

---

### 6. What is error object?

Contains name, message, stack.

---

### 7. Does try-catch work with async?

Only with async/await, not callbacks.

---

### 8. What is throw?

Used to manually throw errors.

---

### 9. Can we throw string?

Yes, but not recommended.

---

### 10. What happens if no catch?

Error propagates upward.

---

### 11. Why avoid empty catch?

It hides bugs.
