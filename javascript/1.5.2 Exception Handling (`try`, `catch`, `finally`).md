## 🧠 Exception Handling (`try`, `catch`, `finally`) – JavaScript

---

## 🔹 Definition

Exception handling is used to **handle runtime errors gracefully without breaking the application**.

👉 In simple terms:

> “Try to execute code → if error occurs → catch it → optionally clean up”

💡 Prevents app crashes and improves user experience.

---

## 🔹 Core Explanation

---

### ✅ 1. `try` Block

```js
try {
  // risky code
}
```

🧠 How it works:

- Code inside `try` is executed normally
- If **no error** → `catch` is skipped
- If **error occurs** → execution jumps to `catch`

💡 Only catches **runtime errors**, not syntax errors.

---

### ✅ 2. `catch` Block

```js
catch (error) {
  console.log(error.message);
}
```

🧠 Key points:

- Executes only when an error occurs in `try`
- Receives error object (`name`, `message`, `stack`)
- Prevents application crash

---

### ✅ 3. `finally` Block

```js
finally {
  // always runs
}
```

🧠 Behavior:

- Runs **always** (error or no error)
- Used for cleanup (closing resources, loaders, etc.)

---

### 🔁 Execution Flow Summary

```text
try → (error?) → catch → finally
        ↓
      no error → finally
```

---

## 🔹 Example(s) with Code

---

### ✅ Example 1: Basic Error Handling

```js
try {
  let result = 10 / 0;
  console.log(result);
} catch (err) {
  console.log("Error occurred:", err.message);
} finally {
  console.log("Execution completed");
}
```

🧠 Output:

- `10 / 0` is valid → no error
- `catch` skipped
- `finally` runs

---

### ✅ Example 2: Reference Error

```js
try {
  console.log(a); // not defined
} catch (err) {
  console.log(err.name); // ReferenceError
}
```

🧠 WHY:

- Accessing undefined variable → runtime error
- `catch` handles it safely

---

### ✅ Example 3: Throw Custom Error 🔥

```js
function withdraw(amount) {
  if (amount > 1000) {
    throw new Error("Limit exceeded");
  }
  return "Success";
}

try {
  withdraw(2000);
} catch (err) {
  console.log(err.message);
}
```

🧠 Insight:

- You can manually throw errors using `throw`
- Useful for validation and business logic

---

### ✅ Example 4: Finally Always Runs ⚠️

```js
try {
  return "From try";
} catch {
  return "From catch";
} finally {
  console.log("Finally runs");
}
```

🧠 Output:

```text
Finally runs
From try
```

💡 Even with `return`, `finally` executes

## 🔹 Real-world Use Cases

---

### 🌐 1. API Calls

```js
try {
  const data = await fetchData();
} catch (err) {
  showError("Failed to fetch data");
}
```

👉 Prevents UI crash on API failure

---

### 🔐 2. JSON Parsing

```js
try {
  JSON.parse(invalidData);
} catch {
  console.log("Invalid JSON");
}
```

---

### 📂 3. LocalStorage Access

```js
try {
  localStorage.setItem("key", value);
} catch (e) {
  console.log("Storage error");
}
```

---

## 🔹 When to Use / When NOT to Use

---

### ✅ Use

- Handling unpredictable runtime errors
- API calls, parsing, async operations
- Critical sections that must not crash

---

### ❌ Avoid

- Using for normal control flow (bad practice)
- Wrapping large blocks unnecessarily
- Ignoring errors silently

---

## 🔹 Common Mistakes / Traps

---

### ❌ Mistake 1: Catching Syntax Errors

```js
try {
  let a = ; ❌
}
```

👉 Syntax errors occur before execution → not caught

---

### ❌ Mistake 2: Empty Catch Block

```js
catch (e) {}
```

👉 Swallowing errors = debugging nightmare

---

### ❌ Mistake 3: Overusing try-catch

👉 Slows performance if used excessively

---

### ❌ Mistake 4: Not re-throwing errors

```js
catch (e) {
  console.log(e);
}
```

👉 Sometimes you should:

```js
throw e;
```

## 🔹 Interview Q&A

---

### ❓1. What is exception handling?

Handling runtime errors using `try-catch` to prevent application crashes.

---

### ❓2. Does `try-catch` catch all errors?

❌ No, only runtime errors (not syntax errors).

---

### ❓3. Is `finally` always executed?

✅ Yes, even if `return` or error occurs.

---

### ❓4. Can we use `try` without `catch`?

✅ Yes, with `finally`.

---

### ❓5. What is `throw`?

Used to manually create and throw errors.

---

### ❓6. Can we omit error parameter in catch?

✅ Yes (ES2019+):

```js
catch {}
```

---

### ❓7. Does try-catch work with async code?

❌ Not directly for promises unless using `await`.

---

### ❓8. How to handle async errors?

```js
try {
  await asyncFunc();
} catch (e) {}
```

## 🔹 Advantages / Pitfalls

---

### ✅ Advantages

- Prevents app crashes
- Improves debugging
- Handles unexpected scenarios

---

### ❌ Pitfalls

- Performance overhead
- Can hide bugs if misused
- Hard to debug if errors swallowed

---

## 🔹 Best Practices

---

✔ Keep `try` block small
✔ Always log or handle errors properly
✔ Use `finally` for cleanup
✔ Use custom errors (`new Error()`)
✔ Avoid silent failures

---

## 🔹 Senior-Level Insights 🚀

---

### ⚡ Performance

- `try-catch` is optimized in modern engines
- But avoid wrapping large code blocks unnecessarily

---

### 🧠 Error Boundaries Thinking (Frontend)

- In React → use error boundaries instead of try-catch for UI
- Try-catch works for **logic**, not UI rendering

---

### 🔄 Async Handling Strategy

| Case        | Approach   |
| ----------- | ---------- |
| Sync code   | try-catch  |
| Async/await | try-catch  |
| Promises    | `.catch()` |

---

### ⚖️ Trade-offs

| Approach  | Pros                 | Cons            |
| --------- | -------------------- | --------------- |
| try-catch | Clean error handling | Slight overhead |
| .catch()  | Promise-friendly     | Less readable   |

---
