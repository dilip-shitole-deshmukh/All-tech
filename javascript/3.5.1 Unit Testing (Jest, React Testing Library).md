## 🧪 Unit Testing: Jest & React Testing Library (Deep Dive)

This is a **🟡 Conceptual + Practical Topic**, but interviewers often expect **real-world testing strategy + best practices**, so we’ll cover **HOW + WHY + pitfalls**.

---

# 🔹 Definition

👉 **Unit Testing** is the process of testing **individual units (functions/components)** in isolation to ensure they work correctly.

- Focuses on **small, independent pieces of code**
- Helps catch bugs early

💡 Simple interview line:

> “Unit testing verifies individual parts of the application in isolation to ensure correctness.”

---

# 🔹 Key Tools

---

## 🧪 Jest

👉 A **testing framework + runner**

- Runs tests
- Provides assertions (`expect`)
- Supports mocking, snapshots

---

## ⚛️ React Testing Library

👉 A library for testing React components

- Focuses on **user behavior (not implementation)**
- Encourages **testing like a user**

---

💡 Key difference:

- Jest → runs tests
- RTL → helps test UI

---

# 🔹 Core Concepts

---

## 🧠 1. Test Structure (Jest)

```js id="test1"
test("adds numbers", () => {
  expect(1 + 2).toBe(3);
});
```

---

### 🔍 Components:

- `test()` → defines test
- `expect()` → assertion
- `toBe()` → matcher

---

## ⚙️ 2. Arrange → Act → Assert (AAA Pattern)

👉 Standard testing flow:

1. Arrange → setup data
2. Act → execute function
3. Assert → verify result

---

## 🧠 WHY:

- Makes tests readable and structured

---

## ⚛️ 3. React Testing Library Philosophy

👉 “Test what users see, not implementation details”

❌ Bad:

```js id="rtl1"
expect(component.state.count).toBe(1);
```

---

✅ Good:

```js id="rtl2"
expect(screen.getByText("1")).toBeInTheDocument();
```

---

💡 Focus on:

- DOM output
- User interaction

---

# 🔹 Example (React Component Test)

---

## 🧩 Component

```jsx id="comp1"
function Counter() {
  const [count, setCount] = React.useState(0);

  return (
    <>
      <span>{count}</span>
      <button onClick={() => setCount(count + 1)}>Increment</button>
    </>
  );
}
```

---

## 🧪 Test

```js id="test2"
import { render, screen, fireEvent } from "@testing-library/react";

test("increments counter", () => {
  render(<Counter />);

  const button = screen.getByText("Increment");

  fireEvent.click(button);

  expect(screen.getByText("1")).toBeInTheDocument();
});
```

---

## 🧠 Execution

1. Render component
2. Find button
3. Simulate click
4. Assert updated UI

👉 Tests real user interaction

# 🔹 Mocking (Important for Interviews)

---

## 🔧 Example: Mock API

```js id="mock1"
jest.mock("./api", () => ({
  fetchData: jest.fn(() => Promise.resolve("data")),
}));
```

---

## 🧠 WHY:

- Avoid real API calls
- Control test behavior

# 🔹 When to Use / NOT Use

---

### ✅ Use Unit Testing when:

- Testing logic in isolation
- Ensuring component behavior

---

### ❌ Avoid relying only on unit tests:

- Doesn’t test full app flow
  👉 Use integration/e2e tests too

---

# 🔹 Common Mistakes / Traps

---

## ❌ Testing implementation details

👉 Leads to fragile tests

---

## ❌ Over-mocking

👉 Tests become unrealistic

---

## ❌ Ignoring async behavior

```js id="test3"
await screen.findByText("data");
```

👉 Must handle async properly

---

## ❌ Using wrong queries

```js id="test4"
getByTestId ❌ (last resort)
getByRole ✅ (preferred)
```

---

# 🔹 Advantages & Pitfalls

---

## ✅ Advantages

- Catch bugs early
- Improve code quality
- Enable safe refactoring

---

## ⚠️ Pitfalls

- Time-consuming
- Poor tests = false confidence
- Maintenance overhead

---

# 🔹 Best Practices

✔ Test user behavior, not internals
✔ Use meaningful test names
✔ Keep tests independent
✔ Use proper queries (`getByRole`)
✔ Avoid unnecessary mocks
✔ Handle async properly

---

# 🔹 Senior-Level Insights 🧠

---

## ⚡ 1. Testing Pyramid

```id="pyr1"
       E2E
    Integration
  Unit (base)
```

👉 Most tests should be unit tests

---

## 🔄 2. Trade-off: Speed vs Coverage

| Type | Speed | Coverage |
| ---- | ----- | -------- |
| Unit | Fast  | Low      |
| E2E  | Slow  | High     |

---

## 🧠 3. Test Stability

- Flaky tests = bad tests
  👉 Ensure deterministic behavior

---

## ⚙️ 4. Accessibility-based Testing

👉 RTL encourages:

```js id="rtl3"
getByRole("button", { name: /submit/i });
```

💡 Improves accessibility + reliability

---

## 📊 5. CI/CD Integration

- Run tests in pipeline
- Prevent broken code deployment

# 🔹 Interview Q&A 🎯

---

### 1. What is unit testing?

Testing individual units of code in isolation.

---

### 2. What is Jest?

A JavaScript testing framework for running tests and assertions.

---

### 3. What is React Testing Library?

A library to test React components based on user behavior.

---

### 4. Why prefer RTL over Enzyme?

RTL focuses on user behavior, not implementation details.

---

### 5. What is mocking?

Replacing real dependencies with fake ones in tests.

---

### 6. What is AAA pattern?

Arrange, Act, Assert structure for tests.

---

### 7. How to test async code?

Using async/await and `findBy` queries.

---

### 8. What is snapshot testing?

Comparing UI output with saved snapshot.

---

### 9. What is test pyramid?

Strategy prioritizing unit tests over integration and e2e.

---

### 10. Why avoid testing implementation details?

Because tests become brittle and break easily.

---

# ✅ Final Summary (Interview Answer)

👉 “Unit testing ensures individual components and functions work correctly. Jest is used as the testing framework, while React Testing Library focuses on testing components from a user’s perspective. The goal is to write reliable, maintainable tests that validate behavior rather than implementation.”
