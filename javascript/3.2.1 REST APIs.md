## 🌐 REST APIs (Deep Dive for Frontend Interviews)

This is a **🟡 Conceptual + Practical Topic**, but interviewers often push toward **design + real-world usage**, so we’ll go moderately deep (with some senior insights).

---

# 🔹 Definition

👉 **REST (Representational State Transfer)** is an architectural style for designing networked APIs using **HTTP protocols**.

- It treats everything as a **resource** (e.g., users, products)
- Uses standard HTTP methods (GET, POST, etc.) to interact with those resources

💡 Simple way to say in interview:

> “REST APIs allow client and server to communicate using standard HTTP methods around resources.”

---

# 🔹 Core Concepts

## 🧩 1. Resources (Heart of REST)

- Everything in REST is a **resource**
- Each resource is identified by a **URL**

👉 Examples:

```
/users
/users/101
/products/50
```

💡 Think:

> Resource = “object/data” exposed via API

---

## 🔄 2. HTTP Methods (CRUD Mapping)

| Method | Operation      | Example      |
| ------ | -------------- | ------------ |
| GET    | Read           | Get users    |
| POST   | Create         | Add user     |
| PUT    | Update         | Replace user |
| PATCH  | Partial update | Update email |
| DELETE | Delete         | Remove user  |

---

### 💡 Important Interview Insight:

- **PUT** → replaces entire resource
- **PATCH** → updates only specific fields

---

## 📦 3. Statelessness (Very Important)

👉 Each request must contain **all required information**

- Server does NOT store client session state
- Every request is independent

💡 Why:

- Improves scalability
- Easier load balancing

---

## 🧾 4. Representation (JSON, XML)

- Client and server exchange data in formats like:
  - JSON (most common)
  - XML (legacy)

Example:

```json
{
  "id": 1,
  "name": "Dilip"
}
```

---

## 🔗 5. Endpoints Structure

👉 Good REST APIs follow predictable patterns:

```
GET    /users        → list users
GET    /users/1      → get user
POST   /users        → create user
PUT    /users/1      → update user
DELETE /users/1      → delete user
```

---

## 📊 6. Status Codes (Critical for Interviews)

| Code | Meaning      |
| ---- | ------------ |
| 200  | Success      |
| 201  | Created      |
| 204  | No content   |
| 400  | Bad request  |
| 401  | Unauthorized |
| 403  | Forbidden    |
| 404  | Not found    |
| 500  | Server error |

💡 Always mention status codes in interviews!

---

# 🔹 How It Works (Frontend Perspective)

👉 Flow:

1. Frontend sends HTTP request (fetch/Axios)
2. Server processes request
3. Server returns response (JSON + status code)
4. Frontend updates UI

---

## 🔧 Example (Frontend API Call)

```js id="rest1"
async function getUsers() {
  const res = await fetch("/api/users");
  const data = await res.json();
  console.log(data);
}
```

---

## 🧠 Execution Flow

- `fetch()` sends GET request
- Server responds with JSON
- `.json()` parses response
- UI updates

# 🔹 When to Use / NOT Use

### ✅ Use REST when:

- CRUD-based systems
- Standard web apps
- Simplicity is preferred

---

### ❌ Avoid REST when:

- Complex queries (GraphQL better)
- Real-time systems (WebSockets better)

---

# 🔹 Common Mistakes / Traps

## ❌ “REST = HTTP”

👉 Wrong

- REST is an **architecture style**, HTTP is protocol

---

## ❌ Using verbs in URLs

```bash
/getUsers ❌
```

```bash
/users ✅
```

💡 Use nouns, not actions

---

## ❌ Ignoring status codes

👉 Returning 200 for everything is bad practice

---

## ❌ Stateful APIs

👉 Storing session on server breaks REST principle

---

# 🔹 Advantages & Pitfalls

## ✅ Advantages

- Simple and widely used
- Scalable due to statelessness
- Works well with HTTP caching

---

## ⚠️ Pitfalls

- Over-fetching / under-fetching
- Multiple API calls needed
- Not ideal for complex data relationships

---

# 🔹 Best Practices

✔ Use proper HTTP methods
✔ Follow RESTful naming conventions
✔ Use meaningful status codes
✔ Handle errors properly
✔ Use pagination for large data
✔ Secure APIs (JWT, OAuth)

---

# 🔹 Senior-Level Insights 🧠

## ⚡ 1. Performance Optimization

- Use **caching (HTTP cache headers)**
- Reduce API calls via batching
- Enable compression (gzip, brotli)

---

## 🔄 2. Idempotency (Important Concept)

👉 Idempotent = same result no matter how many times you call it

- GET, PUT, DELETE → idempotent
- POST → NOT idempotent

💡 Example:

- Calling DELETE multiple times → same result

---

## 📊 3. Versioning APIs

```
/api/v1/users
/api/v2/users
```

👉 Prevents breaking frontend when backend changes

---

## 🔐 4. Security

- Use HTTPS
- Authentication (JWT tokens)
- Rate limiting

# 🔹 Interview Q&A 🎯

### 1. What is REST API?

An architectural style for building APIs using HTTP methods and treating data as resources.

---

### 2. What is statelessness?

Each request contains all information needed, and the server does not store client state.

---

### 3. Difference between PUT and PATCH?

PUT replaces entire resource, PATCH updates partial fields.

---

### 4. What are idempotent methods?

Methods that produce the same result even if called multiple times (GET, PUT, DELETE).

---

### 5. Why use REST?

Simple, scalable, widely supported, and works well with HTTP.

---

### 6. What are status codes?

Standard HTTP response codes indicating success or failure of a request.

---

### 7. What is endpoint?

A URL where an API resource is accessed.

---

### 8. What is over-fetching?

Fetching more data than needed (common issue in REST).

---

### 9. REST vs GraphQL?

REST uses multiple endpoints, GraphQL uses a single endpoint with flexible queries.

---

### 10. How do you secure REST APIs?

Using HTTPS, authentication tokens, and proper authorization mechanisms.

---

# ✅ Final Summary (Interview Answer)

👉 “REST APIs follow an architectural style where resources are accessed using standard HTTP methods like GET, POST, PUT, and DELETE. They are stateless, scalable, and commonly used in frontend-backend communication. Proper use of endpoints, status codes, and HTTP semantics is key to building efficient RESTful systems.”
